# Права клиента и обновление RBAC

Все запросы требуют Bearer-токен. Клиент использует ответ сервера для доступности существующих действий; сервер повторно проверяет права при выполнении операции.

`GET /api/v1/workspaces/{workspaceId}/capabilities` возвращает `{ "workspaceId": "<UUID>", "actions": ["channel.view", "message.write"] }`. `actions` — эффективный union базовых масок назначенных ролей текущего пользователя. Отсутствие права в массиве означает запрет. Отсутствие членства возвращает 404 с кодом `resource_not_found_or_not_visible`.

`GET /api/v1/channels/{channelId}/capabilities` возвращает `{ "channelId": "<UUID>", "workspaceId": "<UUID>", "actions": [...] }`. Базовая маска последовательно получает категорийные, канальные и персональные overrides. В одном слое deny имеет приоритет над grant. Персональный grant перекрывает deny ролей; персональный deny имеет наивысший приоритет. Owner сохраняет доступ независимо от overrides. Архивный статус канала дополнительно запрещает отправку сообщений.

Для приватного канала базовое `channel.view` не открывает доступ. Нужны явное членство в канале или grant в категорийном, канальном либо персональном слое. Последующий deny может закрыть доступ явно добавленному участнику. Публичные каналы также учитывают deny `channel.view`. Список каналов и прямой доступ используют одинаковое правило. Недоступный канал возвращает 404 с кодом `resource_not_found_or_not_visible`. Для DM проверяется членство в DM; ответ содержит права на просмотр, отправку, реакции, вложения и упоминания.

`GET /api/v1/workspaces/{workspaceId}/channels` включает в каждую видимую запись `actions` текущего пользователя. Контекст ролей и overrides загружается пакетно; запросы к БД не повторяются для каждого action или канала. Управление ролями, категориями, участниками и параметрами каналов использует workspace-права там, где существующий endpoint проверяет workspace-контекст. Отдельные возможности отправки, реакций и вложений используют канальные права.

После изменения ролей, назначений, primary role, прав категории/канала/пользователя, членства в канале или удаления участника сервер публикует журналируемое workspace-событие `permissions.updated` с payload `{ "workspaceId": "<UUID>" }`. Изменение параметров канала также публикует invalidation, поскольку приватность и категория меняют видимость. Событие не раскрывает маски или персональные overrides. Клиент объединяет последовательные invalidations и перечитывает только выбранный workspace; presence и typing не вызывают загрузку прав. При потере доступа клиент очищает текущий канал и его сообщения, блокирует composer и выходит из недоступного голосового канала.

Совместимость с v0.2.0: только 404 отсутствующего маршрута без API-кода (`http_error`) включает прежнюю проверку по primary role и видимое уведомление о режиме совместимости. 403, API-404 `resource_not_found_or_not_visible`, сетевые ошибки и некорректные ответы не включают fallback; клиент блокирует действия до успешной проверки.

Формальный контракт чтения данных: общий пакет `libs/shared-go/channelacl` читает membership и базовые маски через `workspace_members`, `workspace_role_members`, `workspace_roles`; канальный snapshot добавляет `channels`, `channel_members`, `category_role_overrides`, `channel_role_overrides`, `channel_user_overrides`. Модуль `permission` предоставляет тонкие aliases. Модули `workspace` и `channel` получают эффективный список через `permission.LoadWorkspace` / `LoadChannels` / `Snapshot.Actions`, не дублируя вычисление слоёв в UI или SQL-фильтрах списка.

`channelacl.VisibleChannels(ctx, db, channelIDs, userIDs)` проверяет пакет пар одним запросом и возвращает `map[userID]map[channelID]bool`; отсутствующая запись означает запрет. `VisibleMembers` проверяет один канал и список кандидатов, `VisibleChannel` — одну пару. Пустые или nil списки означают отсутствие кандидатов, а не всех пользователей/каналов. Разрешения не кешируются между событиями. Realtime применяет этот контракт к live-доставке, replay и typing; событие с `channelId` не может раскрыть содержимое пользователю без текущего `channel.view`, включая адресную доставку.

SFU проверяет текущую видимость при подключении, даже если старая запись `channel_participants` сохранилась. Активные соединения повторно проверяются пакетно каждые 5 секунд с таймаутом БД 3 секунды. Потеря видимости, участия, действующей сессии или архивирование закрывают RTP peer и WebSocket; ошибка БД также закрывает соединение, но не удаляет запись участия. Таким образом, отзыв доступа прекращает уже установленный медиапоток независимо от поведения клиента, с задержкой очередной проверки.

Видимость дочернего канала требует `channel.view` у всех его предков. Разрешения дочерней ветки не обходят приватность или запрет родителя; отсутствующий предок и цикл связей блокируют доступ. Правило применяется к существующим веткам, HTTP, спискам каналов, поиску, вложениям, live/replay и уведомлениям.

Mesh signaling `voice.offer`, `voice.answer`, `voice.ice`, `voice.state`, `voice.hangup` требует `channel_id` в каждом payload. Отправитель и адресат должны иметь текущий `channel.view`, действующие сессии и записи `channel_participants` именно в указанном активном voice-канале. Права не кешируются; ошибка ACL блокирует доставку. Адресация только по пользователю доставляет сигнал исключительно его участвующим сессиям. Если заданы одновременно `target_user_id` и `target_session_id`, владелец сессии должен совпадать. Namespace `call.*` сохраняет отдельный контракт прямых звонков.

Worker проверяет текущий `channel.view` одним пакетом для всех получателей задания до создания уведомлений со snippets. `@everyone`/`@here` сначала собирают участников workspace, затем применяют общую ACL, включая приватность, категорийные grants и персональные denies. Ошибка проверки откладывает задание без доставки содержимого. Новое `notification.created` содержит `channelId` в envelope, чтобы live/replay также проверяли доступ.

Массовое упоминание сохраняет `kind: "mention_everyone"` и `payload.mentionKind: "everyone" | "here"`; клиент использует отдельный kind для настройки muteEveryone. Миграция 000042 исправляет ранее неполный CHECK типов `user_notifications`, не меняя существующие типы. При откате записи массовых упоминаний сохраняются как `mention` с исходным payload.

`GET /api/v1/notifications` и `/notifications/count` заново проверяют доступ к каналам исторических payload: отзыв прав или удаление канала скрывает сохранённый snippet и исключает запись из unread count. Проверка выполняется пакетно; список применяет фильтр до limit, поэтому скрытые записи не вытесняют доступную историю из страницы. Ошибка ACL возвращает 500 без содержимого. Уведомления о звонках и дружбе без канального контекста сохраняются; mention/reply/everyone без корректного channelId не раскрываются.
