# Техническое задание
## Проект: модульная платформа коммуникации с десктопным клиентом

---

## 1. Общие положения

### 1.1. Назначение документа
Настоящий документ определяет технические требования к проектированию программной платформы коммуникации с десктопным клиентом и серверной частью, предназначенной для обмена сообщениями, передачи файлов, голосовых и видеозвонков, демонстрации экрана и системного звука.

Документ фиксирует архитектурные принципы, состав модулей, требования к хранению данных, безопасности, сетевой модели и развёртыванию. Документ не содержит календарных оценок, сроков реализации и организационных вопросов.

### 1.2. Назначение системы
Система предназначена для обеспечения коммуникации пользователей в рамках изолированных логических пространств с контролируемым доступом. Система должна поддерживать персональные и групповые сценарии взаимодействия, а также работу как в локальной сети, так и через глобальные сети общего пользования.

### 1.3. Формат использования
Система должна предоставляться в виде десктопного приложения, взаимодействующего с серверной инфраструктурой. Один и тот же программный стек должен поддерживать:

- локальный запуск на персональном компьютере;
- развёртывание на домашнем сервере;
- развёртывание на выделенном сервере или VPS;
- перенос между средами без изменения базовой архитектуры.

---

## 2. Цель системы

Целью системы является разработка модульной кроссплатформенной платформы коммуникации с десктопным клиентом и серверной инфраструктурой, обеспечивающей:

- обмен текстовыми сообщениями;
- передачу файлов, изображений, аудиофайлов и иных вложений;
- голосовые звонки;
- видеозвонки;
- демонстрацию экрана;
- передачу системного звука при демонстрации экрана;
- создание и сопровождение изолированных пространств пользователей;
- разграничение прав доступа внутри пространств;
- безопасную аутентификацию и управление сессиями;
- защищённое хранение и передачу данных;
- эксплуатацию в локальной и глобальной сетевой среде.

Система не должна представлять собой открытую одноранговую сеть, в которой все экземпляры приложений автоматически обнаруживают друг друга и обмениваются данными без централизованного контроля доступа.

---

## 3. Границы системы

### 3.1. В текущий объём системы входят
- десктопный клиент;
- серверные API и realtime-подсистемы;
- подсистема аутентификации и авторизации;
- подсистема пространств, каналов и членства;
- подсистема обмена сообщениями;
- подсистема звонков и демонстрации экрана;
- подсистема работы с файлами и медиа;
- подсистема безопасности и аудита;
- подсистема хранения и обработки данных;
- подсистема мониторинга и диагностики.

### 3.2. В текущий объём системы не входят
- федерация между независимыми инсталляциями;
- распределённая доверенная сеть между экземплярами приложения;
- полностью децентрализованная модель работы;
- обязательная сквозная end-to-end модель шифрования для всех функций;
- серверная видеомикширование типа MCU как обязательный режим;
- автоматическое обнаружение чужих серверов или пространств.

### 3.3. Требование к будущему развитию
Внутренние контракты, идентификаторы и логические границы системы должны проектироваться без жёсткой привязки к single-node допущениям, однако поддержка федерации, распределённой сети и совместного использования ресурсов между независимыми инсталляциями не входит в текущий объём системы и не должна усложнять первую версию.

---

## 4. Архитектурные принципы

### 4.1. Модульность
Система должна состоять из логически выделенных модулей с чётко определённой зоной ответственности. Каждый модуль должен иметь явные входные и выходные контракты.

### 4.2. Слабая связанность
Модули не должны взаимодействовать друг с другом через файловый обмен, прямое чтение внутренних структур хранения другого модуля или неформализованные побочные эффекты.

Недопустимый подход:
- модуль A записывает данные в файл;
- модуль B периодически читает этот файл;
- корректность обмена определяется только соглашением о формате файла.

Допустимый подход:
- синхронное взаимодействие через HTTP API или gRPC;
- асинхронное взаимодействие через брокер сообщений;
- использование Redis для краткоживущего состояния и pub/sub;
- использование объектного хранилища для бинарных данных;
- использование реляционной базы данных как транзакционного источника истины для предметной модели.

### 4.3. Разделение управляющего и медийного контуров
Система должна разделять:
- управляющий контур: аутентификация, пространства, каналы, метаданные сообщений, сигналинг, права доступа;
- контур передачи данных: файлы, медиаобъекты, WebRTC-потоки, демонстрация экрана, аудио и видео.

### 4.4. Конфигурируемость
Все параметры внешней среды должны задаваться через конфигурацию:
- адреса сервисов;
- домены;
- порты;
- параметры БД;
- параметры Redis и брокера;
- параметры object storage;
- сертификаты;
- STUN/TURN;
- лимиты;
- feature flags.

Запрещается жёстко фиксировать в исходном коде пути, IP-адреса, токены, секреты и environment-specific настройки.

### 4.5. Переносимость
Один и тот же логический состав системы должен поддерживать:
- локальную разработку;
- single-node развёртывание;
- раздельное развёртывание сервисов.

### 4.6. Наблюдаемость
Каждый модуль должен быть наблюдаемым через логи, метрики, health-check интерфейсы и диагностические события.

### 4.7. Server-authoritative модель
Клиент не является источником истины для общей предметной модели. Решения о правах доступа, членстве, принадлежности к пространствам, видимости каналов, возможности запуска звонков и доступа к данным должны приниматься серверной частью.

---

## 5. Сетевая модель

### 5.1. Общий принцип
Экземпляр клиентского приложения должен подключаться только к явно заданному backend endpoint. Система не должна автоматически обнаруживать другие установки приложения, другие серверы и чужие пространства.

### 5.2. Локальный режим
Система должна поддерживать работу в локальной сети:
- доступ по локальному IP или локальному DNS;
- развёртывание без обязательного публичного домена;
- единая модель данных и авторизации;
- возможность использования для тестирования и внутренней эксплуатации.

### 5.3. Глобальный режим
Система должна поддерживать работу через интернет:
- публичный endpoint;
- TLS;
- удалённый доступ к API и realtime-подсистеме;
- работа клиентов из различных сетей;
- поддержка NAT traversal для звонков и демонстрации экрана.

### 5.4. Единство архитектуры
Локальный и глобальный режимы не должны представлять собой две разные системы. Отличия между ними должны определяться конфигурацией deployment-а, а не изменением логики системы.

### 5.5. Работа вне локальной сети
Для полноценной работы вне локальной сети должны быть предусмотрены:
- публично доступный API gateway;
- публично доступный realtime endpoint;
- сигнальный сервер;
- STUN/TURN инфраструктура;
- маршрутизация и защита внешнего трафика;
- механизмы переподключения и восстановления состояния клиента.

---

## 6. Модель предметной области

### 6.1. Основные сущности
Система должна оперировать следующими базовыми сущностями:

- User — пользователь;
- UserProfile — профиль пользователя;
- DeviceSession — сессия устройства;
- Workspace — изолированное пространство;
- WorkspaceMembership — членство пользователя в пространстве;
- Role — роль в пространстве;
- Permission — право доступа;
- Channel — канал внутри пространства;
- DirectChat — личный диалог;
- GroupChat — групповая беседа;
- Message — сообщение;
- Attachment — вложение;
- Invite — приглашение;
- CallSession — звонок;
- CallParticipant — участник звонка;
- ScreenShareSession — сессия демонстрации экрана;
- MediaObject — медиаобъект;
- AuditEvent — аудиторское событие;
- SecurityEvent — событие безопасности.

### 6.2. Изолированные пространства
Основной логической единицей организации пользователей должна быть сущность Workspace.

Каждое пространство должно:
- иметь уникальный идентификатор;
- иметь владельца или набор администраторов;
- содержать каналы, участников, роли и настройки;
- быть изолированным от других пространств;
- быть недоступным пользователю без членства или приглашения.

### 6.3. Каналы
Внутри пространства должны поддерживаться каналы как минимум следующих типов:
- текстовые;
- голосовые;
- каналы с медиа-сессиями;
- приватные;
- служебные.

### 6.4. Приглашения
Доступ к пространствам должен обеспечиваться через модель приглашений. Приглашения должны поддерживать:
- ограничение срока действия;
- ограничение числа использований;
- возможность отзыва;
- аудит использования;
- привязку к пространству или конкретной области доступа.

### 6.5. Отсутствие глобальной видимости
Новый пользователь после установки приложения, регистрации или входа не должен автоматически видеть:
- пространства других пользователей;
- каналы, в которые он не приглашён;
- списки чужих серверов;
- узлы других deployment-ов.

## 7. Клиентское приложение

### 7.1. Назначение
Десктопный клиент предназначен для взаимодействия пользователя с системой.

### 7.2. Основные функции клиента
Клиент должен обеспечивать:
- регистрацию и вход;
- выбор сервера или backend endpoint;
- работу со списком пространств и каналов;
- обмен сообщениями;
- отправку файлов и медиа;
- голосовые и видеозвонки;
- демонстрацию экрана;
- передачу системного звука там, где это поддерживается ОС;
- отображение статусов пользователей и доставки;
- reconnect и повторную синхронизацию состояния.

### 7.3. Архитектура клиента
Клиент должен быть разделён как минимум на следующие слои:
- UI слой;
- application/use-case слой;
- сетевой слой;
- realtime слой;
- media слой;
- слой локального кэша и настроек.

### 7.4. Ограничения
Клиент не должен:
- принимать решения о правах доступа без сервера;
- быть единственным источником истины для общих данных;
- содержать критичную бизнес-логику, противоречащую серверной модели;
- хранить секреты в небезопасном виде.

---

## 8. Серверная архитектура

### 8.1. Общая структура
Серверная часть должна быть модульной клиент-серверной платформой с выделенными доменными и инфраструктурными компонентами.

### 8.2. Основные серверные модули

#### 8.2.1. API Gateway / Edge Service
Назначение:
- единая внешняя точка входа;
- TLS termination;
- маршрутизация;
- базовая проверка токенов;
- rate limiting;
- request tracing;
- проксирование к внутренним сервисам.

#### 8.2.2. Identity / Auth Service
Назначение:
- регистрация пользователей;
- вход и выход;
- выпуск access и refresh токенов;
- отзыв сессий;
- управление устройствами;
- аутентификация и базовая авторизация.

#### 8.2.3. User / Profile Service
Назначение:
- хранение данных профиля;
- управление аватарами, отображаемыми именами, настройками пользователя;
- управление приватными атрибутами профиля.

#### 8.2.4. Workspace Service
Назначение:
- создание и настройка пространств;
- управление членством;
- управление ролями;
- применение политик доступа;
- базовые операции над пространствами.

#### 8.2.5. Role / Permission Layer
Назначение:
- серверная проверка прав;
- оценка возможности выполнения действий;
- разграничение доступа к пространствам, каналам, сообщениям и звонкам.

Примечание: данный слой может быть реализован как библиотечный или сервисный компонент, но должен существовать как отдельная логическая подсистема.

#### 8.2.6. Chat / Channel Service
Назначение:
- управление каналами и чатами;
- управление составом участников;
- управление настройками каналов;
- подготовка контекста для обмена сообщениями.

#### 8.2.7. Message Service
Назначение:
- создание, изменение и удаление сообщений;
- хранение message metadata;
- управление вложениями на уровне метаданных;
- read receipts, reactions, reply/forward;
- идемпотентность отправки.

#### 8.2.8. Realtime / Presence Service
Назначение:
- online/offline статусы;
- typing indicators;
- краткоживущие realtime-события;
- доставка событий подключённым клиентам.

#### 8.2.9. Invite Service
Назначение:
- создание приглашений;
- отзыв приглашений;
- проверка срока действия и лимитов;
- аудит использования.

#### 8.2.10. Signaling Service
Назначение:
- обмен сигнализацией для звонков и демонстрации экрана;
- обмен SDP/ICE;
- координация подключения участников;
- уведомления о состоянии звонка.

#### 8.2.11. Media Session Orchestrator
Назначение:
- создание и завершение медиа-сессий;
- управление call room состоянием;
- согласование с медиасервером;
- управление участниками и медиа-ролями;
- применение политик качества и ограничений.

#### 8.2.12. Media Node / SFU Layer
Назначение:
- маршрутизация WebRTC-потоков между участниками;
- обработка публикации и подписки на аудио, видео и screen share потоки;
- поддержка масштабируемого многопользовательского звонка.

Базовым подходом должна быть модель SFU. Модель MCU не является обязательной для первой версии.

#### 8.2.13. STUN/TURN Infrastructure
Назначение:
- прохождение медиа через NAT и firewall;
- relay fallback;
- обеспечение работоспособности звонков вне локальной сети.

TURN должен рассматриваться как обязательная часть целевой архитектуры, а не как опциональное дополнение.

#### 8.2.14. File Upload Service
Назначение:
- приём вложений;
- валидация размера и типа;
- размещение файлов в объектном хранилище;
- выдача ссылок и метаданных.

#### 8.2.15. Media Processing Worker
Назначение:
- генерация превью;
- извлечение метаданных;
- обработка аудио/видео превью;
- асинхронная обработка медиа;
- постановка и выполнение фоновых задач.

#### 8.2.16. Notification Service
Назначение:
- генерация пользовательских уведомлений;
- доставка событий о новых сообщениях, приглашениях, пропущенных звонках и иных системных событиях.

#### 8.2.17. Security / Audit Module
Назначение:
- хранение и обработка событий безопасности;
- аудит входов и критичных операций;
- suspicious activity detection;
- журналирование действий администраторов и модераторов.

#### 8.2.18. Admin / Moderation Module
Назначение:
- административное управление системой;
- просмотр диагностической информации;
- модерация пользователей и контента;
- управление ограничениями и блокировками.

#### 8.2.19. Observability Module
Назначение:
- централизованные логи;
- метрики;
- трассировка запросов;
- health и readiness checks;
- диагностические панели.

## 9. Хранилища и данные

### 9.1. Общие требования
Для каждой категории данных должен существовать один понятный источник истины. Разные типы данных должны храниться в специализированных хранилищах.

### 9.2. Основная база данных
Основная реляционная база данных должна использоваться для хранения:
- пользователей;
- профилей;
- credentials metadata;
- пространств;
- членств;
- ролей и политик доступа;
- каналов;
- сообщений и их метаданных;
- приглашений;
- метаданных вложений;
- сессий;
- событий аудита.

### 9.3. Требования к модели БД
Модель данных должна:
- быть нормализованной в пределах разумного;
- иметь явные внешние связи;
- поддерживать транзакционность для критичных операций;
- обеспечивать идемпотентность важных действий;
- поддерживать версионность изменяемых сущностей там, где это требуется;
- поддерживать аудит и трассировку критичных изменений.

### 9.4. Рекомендуемые предметные таблицы
Состав сущностей должен предусматривать как минимум следующие группы:

Пользователи:
- users;
- user_credentials;
- user_sessions;
- user_devices;
- user_profiles.

Пространства:
- workspaces;
- workspace_members;
- workspace_roles;
- workspace_permissions;
- workspace_invites.

Каналы и чаты:
- channels;
- channel_members;
- direct_chats;
- group_chats;
- chat_participants.

Сообщения:
- messages;
- message_revisions;
- message_attachments;
- message_reactions;
- read_receipts.

Звонки и медиа:
- call_sessions;
- call_participants;
- media_tracks_metadata;
- screen_share_sessions;
- call_events.

Файлы:
- media_objects;
- upload_sessions;
- media_processing_jobs.

Безопасность и аудит:
- auth_events;
- audit_log;
- moderation_actions;
- security_events.

### 9.5. Redis
Redis должен использоваться для:
- presence;
- краткоживущего realtime state;
- rate limiting;
- pub/sub;
- кэширования;
- временных токенов и служебных coordination-механизмов.

Redis не должен использоваться как постоянное основное хранилище предметных данных.

### 9.6. Message Broker / Queue
Брокер сообщений должен использоваться для:
- асинхронной обработки;
- фоновых задач;
- fanout событий;
- генерации превью;
- индексации;
- уведомлений;
- вторичных производных операций.

### 9.7. Object Storage
Объектное хранилище должно использоваться для:
- файловых вложений;
- изображений;
- аудио и видеофайлов;
- аватаров;
- экспортов;
- производных медиаобъектов.

Запрещается хранить крупные бинарные объекты в основной реляционной БД как базовый подход.

---

## 10. Взаимодействие модулей

### 10.1. Синхронное взаимодействие
Для операций, требующих немедленного ответа, должно использоваться синхронное взаимодействие через формализованный API.

Примеры:
- вход пользователя;
- получение профиля;
- получение списка пространств и каналов;
- чтение истории сообщений;
- создание пространства;
- получение upload-параметров.

### 10.2. Асинхронное взаимодействие
Для фоновых и производных операций должно использоваться асинхронное взаимодействие через брокер сообщений.

Примеры:
- генерация превью;
- отправка уведомлений;
- обновление индексов;
- аудит действий;
- вторичное обновление счётчиков;
- постобработка медиафайлов.

### 10.3. Ограничения
Модули не должны полагаться на неформальные side effects, прямое чтение чужих внутренних таблиц без контракта и обмен через файловую систему.

---

## 11. Обмен сообщениями

### 11.1. Общие требования
Подсистема сообщений должна обеспечивать:
- доставку сообщений в личные и групповые контексты;
- поддержку текстовых сообщений и вложений;
- поддержку reply, forward, reactions;
- редактирование и удаление сообщений в рамках политики доступа;
- статусы доставки и прочтения;
- корректное поведение при reconnect.

### 11.2. Идемпотентность
Операции отправки сообщений должны быть идемпотентны. Клиент должен иметь возможность безопасно повторить запрос после потери связи, не создавая дубликатов.

### 11.3. Источник истины
Источником истины по сообщениям должна являться серверная часть. Клиент может хранить кэш, но не должен определять окончательный статус сообщения самостоятельно.

---

## 12. Звонки, видео и демонстрация экрана

### 12.1. Общий подход
Подсистема звонков должна строиться на основе WebRTC с разделением:
- сигнализации;
- управления сессией;
- передачи медиа.

### 12.2. Архитектурная модель
Базовая модель первой версии должна предполагать:
- клиентский захват источников;
- клиентское кодирование медиапотоков;
- серверный сигналинг;
- серверную оркестрацию call session;
- маршрутизацию потоков через SFU;
- relay fallback через TURN.

### 12.3. Screen share
Демонстрация экрана должна рассматриваться как отдельный тип медиа-потока. Система должна поддерживать:
- выбор экрана или окна;
- начало и завершение screen share без разрушения звонка;
- отдельные статусы screen share;
- передачу системного звука там, где это технически поддерживается клиентской платформой;
- независимые политики качества для screen share.

### 12.4. Приоритеты медиа
При деградации качества связи система должна поддерживать:
- приоритет аудио над видео;
- приоритет screen share над второстепенными видеопотоками при необходимости;
- ограничение числа одновременно принимаемых потоков;
- адаптацию качества.

### 12.5. TURN
TURN является обязательной частью целевой архитектуры для корректной работы звонков и демонстрации экрана в глобальных сетях.

---

## 13. Аутентификация, авторизация и управление доступом

### 13.1. Регистрация пользователей
Система должна поддерживать регистрацию пользователей с созданием уникальной учётной записи в рамках конкретного deployment-а.

### 13.2. Сессии и устройства
Система должна поддерживать:
- access token;
- refresh token;
- device/session management;
- отзыв сессий;
- аудит входов.

### 13.3. Роли и права
Внутри пространства должна поддерживаться ролевая модель доступа.

Минимально должны быть предусмотрены роли:
- owner;
- admin;
- moderator;
- member;
- guest.

Каждое действие должно проверяться сервером с учётом роли и контекста.

### 13.4. Серверная проверка прав
Клиент может скрывать или показывать элементы интерфейса, однако окончательное решение о доступе к пространствам, каналам, сообщениям, вложениям, звонкам и административным операциям должно приниматься сервером.

### 13.5. Отсутствие автоматического доверия
Наличие установленного приложения не должно давать доступ ни к одному пространству, каналу или ресурсу без явной авторизации и проверки членства.

---

## 14. Безопасность

### 14.1. Общие требования
Система должна проектироваться с учётом безопасности по умолчанию.

### 14.2. Защита передачи данных
Должны быть обеспечены:
- TLS для внешних API соединений;
- защищённые realtime соединения;
- защищённые сигнальные соединения;
- защищённая передача медиа средствами WebRTC;
- защищённые внутренние соединения при необходимости.

### 14.3. Хранение паролей
Пароли пользователей должны храниться только в виде стойких хэшей с солью. Обратимое шифрование паролей запрещается.

### 14.4. Шифрование данных при хранении
Должны быть предусмотрены:
- шифрование диска или тома на уровне инфраструктуры;
- защита резервных копий;
- защита секретов и чувствительных служебных данных;
- возможность шифрования отдельных чувствительных полей на уровне приложения или хранилища.

### 14.5. Шифрование на уровне полей
Отдельное шифрование должно предусматриваться для:
- чувствительных персональных данных;
- служебных секретов;
- приватных токенов, ключей и иных высокочувствительных значений.

### 14.6. Ограничения первой версии
Полноценная сквозная end-to-end модель шифрования для всех сообщений, медиа и вложений не является обязательным требованием первой версии и не должна закладываться ценой чрезмерного усложнения базовой архитектуры.

### 14.7. Дополнительные требования безопасности
Система должна предусматривать:
- rate limiting;
- защиту от brute-force;
- аудит критичных операций;
- журналирование security events;
- серверную валидацию входных данных;
- ограничение размеров и типов вложений;
- безопасную работу с секретами и конфигурацией.

---

## 15. Наблюдаемость и эксплуатация

### 15.1. Логи
Каждый модуль должен формировать структурированные логи с возможностью связывания записей по request id, session id, user id, workspace id и иным идентификаторам контекста.

### 15.2. Метрики
Система должна обеспечивать сбор метрик как минимум по следующим направлениям:
- количество активных пользователей;
- количество активных realtime-соединений;
- количество активных звонков;
- количество участников звонков;
- латентность API;
- ошибки аутентификации;
- ошибки доставки сообщений;
- объём relay-трафика TURN;
- качество ICE-соединений;
- скорость загрузки и обработки файлов.

### 15.3. Диагностика
Каждый сервис должен иметь:
- health endpoint;
- readiness endpoint;
- диагностику зависимости от БД, Redis, брокера и object storage;
- возможность обнаружения degraded state.

---

## 16. Развёртывание

### 16.1. Общие требования
Развёртывание должно поддерживать единый подход для всех сред: локальная разработка, single-node окружение, серверная эксплуатация.

### 16.2. Требования к deployment-модели
Система должна допускать:
- локальный запуск всех компонентов в dev-среде;
- модульный запуск на одном хосте;
- разнос компонентов по разным узлам без изменения предметной модели.

### 16.3. Конфигурация среды
Все настройки среды должны быть внешними по отношению к исходному коду.

### 16.4. Переносимость
Перенос системы между локальным ПК, домашним сервером и удалённым сервером должен требовать изменения конфигурации, а не переписывания логики или взаимодействия модулей.

## 17. Нефункциональные требования

Система должна удовлетворять следующим нефункциональным требованиям:

- модульность;
- переносимость;
- расширяемость;
- наблюдаемость;
- диагностируемость;
- устойчивость к временным сбоям сети;
- безопасное хранение и передача данных;
- предсказуемая модель прав доступа;
- отсутствие несанкционированной глобальной видимости чужих пространств и ресурсов.

## 18. Ограничения и анти-паттерны

### 18.1. Запрещённые архитектурные подходы
Не допускается закладывать в основу системы следующие решения:
- межмодульный обмен через файлы;
- хранение всех типов данных в одном универсальном хранилище без специализации;
- жёсткая сцепка UI и сетевой логики клиента;
- смешивание сигналинга, API и медиапередачи в один неразделённый слой без формальных границ;
- reliance на peer-to-peer модель как на единственный способ групповой коммуникации;
- отсутствие TURN в целевой архитектуре глобального режима;
- предоставление доступа к пространствам без серверной проверки;
- автоматическое раскрытие чужих пространств новым пользователям;
- хранение паролей в обратимо зашифрованном виде.

### 18.2. Ограничения первой версии
Первая версия системы не должна усложняться следующими задачами:
- межсерверная федерация;
- распределённая сеть доверия между deployment-ами;
- полностью децентрализованная маршрутизация;
- обязательный E2EE для всех сценариев;
- MCU как базовый режим медиасервера.

## 22. Детальная модель данных и сущности БД

### 22.1. Общие принципы модели данных

Модель данных должна строиться по следующим принципам:
- реляционная БД является основным транзакционным источником истины;
- каждая сущность имеет стабильный первичный идентификатор;
- связи между сущностями оформляются явно;
- чувствительные поля отделяются от общедоступных атрибутов;
- изменяемые сущности поддерживают временные метки и при необходимости версионность;
- действия, которые могут быть повторены клиентом, должны поддерживать идемпотентность;
- временное сетевое состояние и presence не должны храниться как основная предметная информация в реляционной БД.

### 22.2. Группы сущностей

Предметная модель должна включать следующие группы сущностей:
- пользователи и аутентификация;
- пространства, членство и роли;
- каналы, чаты и сообщения;
- вложения и медиаобъекты;
- звонки и screen share;
- сессии устройств и безопасность;
- аудит и модерация.

## 23. Пользователи и аутентификация

### 23.1. users
Назначение: базовая сущность пользователя.

Основные поля:
- id;
- username или уникальный login identifier;
- account_status;
- created_at;
- updated_at;
- deleted_at или archived_at при необходимости.

Требования:
- username должен быть уникален в рамках deployment-а;
- публичные поля пользователя должны быть отделены от credentials и чувствительных данных;
- мягкое удаление предпочтительнее физического удаления для аудита и ссылочной целостности.

### 23.2. user_profiles
Назначение: отображаемые и профильные данные пользователя.

Основные поля:
- user_id;
- display_name;
- avatar_media_object_id;
- bio/status_text;
- locale;
- timezone;
- profile_visibility_settings;
- updated_at.

Требования:
- профиль должен быть логически отделён от credentials;
- часть полей может попадать под отдельную политику приватности.

### 23.3. user_credentials
Назначение: аутентификационные данные и связанные чувствительные атрибуты.

Основные поля:
- user_id;
- password_hash;
- password_algo_metadata;
- password_changed_at;
- email при использовании email-based login;
- email_verification_state;
- optional encrypted sensitive fields.

Требования:
- пароль хранится только как стойкий hash;
- обратимое шифрование пароля запрещено;
- email и иные чувствительные поля могут храниться отдельно и шифроваться на уровне поля.

### 23.4. user_sessions
Назначение: учёт активных и завершённых сессий пользователя.

Основные поля:
- id;
- user_id;
- device_id;
- refresh_token_reference;
- session_status;
- created_at;
- last_seen_at;
- revoked_at;
- ip_metadata;
- user_agent_metadata.

Требования:
- отзыв сессии должен быть возможен независимо от остальных сессий;
- сервер должен иметь возможность принудительно завершить конкретную сессию.

### 23.5. user_devices
Назначение: привязка и описание устройств пользователя.

Основные поля:
- id;
- user_id;
- device_name;
- platform;
- device_fingerprint или иной контролируемый идентификатор;
- trust_status;
- created_at;
- last_seen_at.

## 24. Пространства, членство и права доступа

### 24.1. workspaces
Назначение: изолированные пространства, аналог серверов/сообществ.

Основные поля:
- id;
- owner_user_id или ownership model;
- name;
- slug или invite-friendly identifier при необходимости;
- visibility_type;
- workspace_status;
- settings_json или выделенные таблицы настроек;
- created_at;
- updated_at.

Требования:
- workspace не должен быть глобально видим без прав доступа;
- модель должна поддерживать закрытые пространства по умолчанию.

### 24.2. workspace_members
Назначение: членство пользователя в пространстве.

Основные поля:

Все ключевые сущности должны иметь устойчивые, уникальные и переносимые идентификаторы. Формат идентификатора должен быть единым в рамках системы.

- created_at;
- updated_at при изменяемости;

### 31.3. Клиентские временные метки
Клиентские временные метки могут использоваться как вспомогательные данные, но не должны быть единственной основой для упорядочивания событий на сервере.

## 32. Ролевая модель и матрица прав доступа

### 32.1. Общие принципы разграничения доступа

Подсистема доступа должна строиться по модели RBAC с возможностью контекстного уточнения прав на уровне пространства и канала.

Основные принципы:
- пользователь получает доступ к ресурсам только после подтверждённого членства;
- права определяются сервером на основании membership, ролей и контекста ресурса;
- права на уровне канала могут сужать или расширять права пространства в рамках заданной политики;
- клиент не является источником истины по разрешениям;
- отсутствие права трактуется как запрет.

### 32.2. Базовые системные роли

В первой версии должны быть предусмотрены следующие системные роли:
- owner;
- admin;
- moderator;
- member;
- guest.

Допускается расширение списка пользовательскими ролями в будущем, однако первая версия должна иметь фиксированный базовый набор системных ролей.

### 32.3. Назначение ролей

#### 32.3.1. Owner
Роль владельца пространства.

Назначение:
- полный административный контроль над пространством;
- управление ролями и политиками доступа;
- управление приглашениями;
- назначение и снятие администраторов и модераторов;
- удаление или архивирование пространства;
- доступ к административному журналу пространства.

#### 32.3.2. Admin
Роль администратора пространства.

Назначение:
- управление каналами;
- управление участниками в пределах предоставленных прав;
- управление приглашениями;
- настройка части параметров пространства;
- участие в модерации;
- управление звонками и каналами в пределах пространства.

#### 32.3.3. Moderator
Роль модератора.

Назначение:
- управление пользовательским контентом;
- ограничение доступа нарушителей;
- удаление сообщений;
- временные санкции;
- управление порядком в каналах без полного административного контроля над пространством.

#### 32.3.4. Member
Базовая роль участника пространства.

Назначение:
- доступ к разрешённым каналам;
- отправка сообщений;
- участие в звонках;
- загрузка файлов в пределах лимитов;
- использование базовых функций пространства.

#### 32.3.5. Guest
Ограниченная роль.

Назначение:
- доступ только к ограниченному набору каналов или функций;
- ограниченные права на чтение, участие в звонках или обмен сообщениями в зависимости от политики пространства.

### 32.4. Категории прав доступа

Права доступа должны быть сгруппированы по предметным категориям.

#### 32.4.1. Права пространства

### 32.5. Базовая матрица прав доступа

Ниже определяется базовая матрица прав для первой версии. Конкретные пространства могут дополнительно ограничивать права через настройки и channel-level overrides.

#### 32.5.1. Owner
Owner должен иметь полный доступ ко всем категориям операций в пределах пространства.

#### 32.5.2. Admin
Admin должен иметь право:
- просматривать пространство и список участников;
- создавать, изменять и удалять каналы;
- управлять приглашениями;
- просматривать и изменять часть настроек пространства;
- управлять участниками в пределах политики пространства;
- запускать и администрировать звонки;
- демонстрировать экран;
- удалять любые сообщения;
- просматривать журнал аудита пространства, если это не ограничено отдельной политикой.

Admin не должен автоматически иметь право:
- менять владельца пространства;
- необратимо удалять пространство без отдельного разрешения;
- изменять критичные security-настройки верхнего уровня deployment-а.

#### 32.5.3. Moderator
Moderator должен иметь право:
- просматривать разрешённые каналы;
- отправлять сообщения;
- удалять чужие сообщения в пределах назначенной области ответственности;
- применять ограниченные санкции к участникам;
- просматривать журнал модерации;
- участвовать в звонках и демонстрировать экран, если это разрешено политикой пространства.

Moderator не должен автоматически иметь право:
- создавать или удалять пространство;
- управлять ролями верхнего уровня;
- назначать администраторов;
- изменять системные security-параметры пространства.

#### 32.5.4. Member
Member должен иметь право:
- просматривать доступные ему каналы;
- отправлять сообщения;
- редактировать и удалять собственные сообщения в рамках политики;
- добавлять реакции;
- загружать вложения в пределах лимитов;
- участвовать в звонках;
- включать микрофон, камеру и screen share в разрешённых каналах.

Member не должен автоматически иметь право:
- видеть приватные каналы без явного доступа;
- удалять чужие сообщения;
- управлять ролями;
- приглашать пользователей, если это отключено политикой пространства;
- изменять настройки пространства.

#### 32.5.5. Guest
Guest должен иметь право только на минимальный набор функций, определённый политикой пространства.

Базово guest может получать:
- доступ на чтение к ограниченным каналам;
- доступ к участию в некоторых обсуждениях;
- доступ к звонку или просмотру контента, если это явно разрешено.

Guest не должен автоматически иметь право:
- видеть все каналы пространства;
- приглашать новых пользователей;
- загружать файлы без отдельного разрешения;
- запускать звонки;
- управлять участниками.

### 32.6. Приоритеты и разрешение конфликтов

При одновременном наличии нескольких ролей или правил должны применяться следующие принципы:
- deny имеет приоритет над allow, если политика явно не определяет иное;
- channel-level ограничения могут дополнительно запрещать операции, разрешённые на уровне пространства;
- системные роли owner и admin могут иметь защищённый набор прав, который нельзя полностью обнулить без специальной логики;
- приватный канал должен требовать либо явного членства, либо явного channel-level разрешения.

### 32.7. Проверка прав на сервере

Каждое действие пользователя, связанное с доступом к данным или управлением ресурсами, должно проверяться сервером.

Минимально сервер обязан проверять:
- право видеть пространство;
- право видеть конкретный канал;
- право отправлять сообщение в конкретный канал;
- право загружать вложения;
- право присоединяться к звонку;
- право запускать screen share;
- право выдавать приглашения;
- право удалять сообщения;
- право применять санкции к участникам.

### 32.8. Наследование прав

В первой версии рекомендуется следующая модель наследования:
- базовые права определяются ролью в пространстве;
- channel-level overrides применяются поверх базовой роли;
- приватные каналы используют явное членство или явный allow-list;
- для direct chats права определяются составом участников и системными правилами, а не ролями workspace.

### 32.9. Аудит действий, связанных с правами

Следующие действия должны обязательно журналироваться:
- создание и удаление ролей;
- изменение набора прав роли;
- назначение и снятие роли;
- создание, отзыв и использование приглашения;
- исключение, блокировка и восстановление участника;
- удаление сообщений модератором или администратором;
- изменение видимости канала;
- изменение channel-level permissions.

### 32.10. Требования к расширяемости ролевой модели

Ролевая модель первой версии должна оставлять возможность для дальнейшего расширения без разрушения существующей схемы. Для этого:
- permission codes должны быть атомарными и стабильными;
- проверка прав должна быть централизованной;
- роли не должны быть жёстко зашиты в UI как единственный источник поведения;
- модель должна поддерживать добавление пользовательских ролей в будущих версиях.

## 33. Функциональные требования верхнего уровня

### 33.1. Общие положения

Функциональные требования определяют набор пользовательских и административных возможностей системы, обязательных для корректной работы первой полноценной версии.

### 33.2. Управление учётными записями
Система должна обеспечивать:
- регистрацию пользователя;
- вход пользователя;
- выход из текущей сессии;
- отзыв других активных сессий при наличии интерфейса управления устройствами;
- просмотр базовой информации о собственном профиле;
- изменение отображаемого имени, аватара и части настроек профиля.

### 33.3. Управление пространствами
Система должна обеспечивать:
- создание пространства;
- настройку базовых параметров пространства;
- приглашение пользователей в пространство;
- вступление по приглашению;
- просмотр списка участников;
- назначение ролей при наличии соответствующих прав;
- исключение участника или ограничение его доступа при наличии соответствующих прав.

### 33.4. Управление каналами
Система должна обеспечивать:
- создание текстовых каналов;
- создание голосовых или медиа-каналов;
- изменение базовых параметров канала;
- управление приватностью канала;
- удаление или архивирование канала при наличии прав.

### 33.5. Обмен сообщениями
Система должна обеспечивать:
- отправку текстовых сообщений;
- получение новых сообщений в realtime-режиме;
- загрузку истории сообщений;
- редактирование собственных сообщений в рамках политики;
- удаление собственных сообщений в рамках политики;
- удаление чужих сообщений при наличии прав;
- реакции на сообщения;
- отправку ответов и пересылок при поддержке соответствующих типов сообщений.

### 33.6. Передача вложений
Система должна обеспечивать:
- загрузку файлов и медиа;
- прикрепление вложений к сообщениям;
- получение и скачивание вложений при наличии прав доступа к исходному сообщению и контексту;
- асинхронную обработку вложений;
- отображение статуса загрузки и обработки.

### 33.7. Presence и realtime-события
Система должна обеспечивать:
- отображение online/offline статусов;
- обновление статусов подключения;
- typing indicators при наличии такой функции;
- доставку служебных realtime-событий клиентам.

### 33.8. Звонки
Система должна обеспечивать:
- создание звонка в допустимом контексте;
- присоединение пользователей к звонку;
- выход из звонка;
- управление собственным микрофоном и камерой;
- отображение состояния участников;
- завершение звонка;
- обработку сетевых сбоев и повторное подключение в рамках допустимой логики.

### 33.9. Демонстрация экрана
Система должна обеспечивать:
- запуск демонстрации экрана;
- завершение демонстрации экрана;
- публикацию screen share как отдельного потока;
- передачу системного звука при технической поддержке на платформе клиента;
- корректное отображение состояния screen share другим участникам.

### 33.10. Модерация и административные действия
Система должна обеспечивать:
- удаление сообщений модератором или администратором;
- временное ограничение пользователя;
- исключение пользователя из пространства;
- блокировку пользователя в пространстве;
- просмотр журнала ключевых административных и модераторских действий при наличии прав.

### 33.11. Безопасность и управление сессиями
Система должна обеспечивать:
- защищённую аутентификацию;
- хранение пароля только в виде hash;
- работу access и refresh токенов;
- отзыв сессий;
- аудит входов;
- базовую защиту от злоупотреблений при аутентификации и работе с приглашениями.

### 33.12. Диагностика и эксплуатация
Система должна обеспечивать:
- журналирование системных событий;
- сбор диагностических метрик;
- health-check интерфейсы;
- базовую административную диагностику состояния модулей и ключевых зависимостей.

## 34. Нефункциональные требования

### 34.1. Общие положения

Нефункциональные требования определяют ограничения, свойства качества и эксплуатационные ожидания, которым должна соответствовать система независимо от конкретных пользовательских сценариев.

### 34.2. Требования к архитектурной устойчивости
Система должна:
- сохранять работоспособность при временной недоступности отдельных некритичных компонентов;
- иметь контролируемое поведение при деградации зависимостей;
- обеспечивать предсказуемую обработку ошибок;
- не допускать неявной потери данных при кратковременных сетевых сбоях;
- поддерживать перезапуск отдельных модулей без полной остановки всей платформы, если это не противоречит выбранной deployment-модели.

### 34.3. Требования к переносимости
Система должна:
- запускаться в локальной среде разработки;
- запускаться в single-node режиме на одном хосте;
- поддерживать перенос на удалённый сервер без изменения предметной логики;
- не зависеть от уникальных характеристик конкретной машины;
- использовать внешнюю конфигурацию и внешнее хранение секретов.

### 34.4. Требования к масштабируемости
Архитектура должна допускать:
- вертикальное масштабирование на одном сервере;
- горизонтальное масштабирование realtime и stateless-компонентов;
- вынесение объектного хранилища, брокера и Redis за пределы одного процесса;
- разделение нагрузки между API, realtime и media-подсистемами.

Первая версия не обязана быть полностью горизонтально масштабируемой по всем компонентам, но архитектурные решения не должны блокировать такой переход в будущем.

### 34.5. Требования к производительности API
Система должна обеспечивать приемлемое время отклика для интерактивных пользовательских операций.

Для первой версии следует закладывать следующие целевые ориентиры:
- типовые CRUD-операции интерфейса должны выполняться без заметной пользователю задержки при штатной нагрузке;
- операции входа, загрузки списка пространств и каналов, чтения истории и отправки сообщений должны относиться к интерактивному классу операций;
- длительные операции должны быть вынесены в асинхронные процессы и сопровождаться статусом выполнения.

Точные численные SLO могут быть утверждены отдельно, однако архитектура не должна предполагать, что пользователь готов ждать завершения фоновой обработки в синхронном запросе.

### 34.6. Требования к realtime-подсистеме
Realtime-подсистема должна:
- поддерживать устойчивые постоянные соединения клиентов;
- корректно обрабатывать переподключение;
- обеспечивать повторную синхронизацию состояния после reconnect;
- не терять критичные события без возможности догрузки или восстановления;
- отделять краткоживущие presence-события от долговременных предметных данных.

### 34.7. Требования к звонкам и медиа
Подсистема звонков должна:
- поддерживать деградацию качества при ухудшении сети;
- сохранять приоритет аудио над видео;
- поддерживать отдельную логику для screen share;
- не требовать обязательного серверного перекодирования всех потоков в первой версии;
- корректно обрабатывать частичный отказ медиапотоков без разрушения всей сессии;
- поддерживать TURN fallback в неблагоприятных сетевых условиях.

### 34.8. Требования к консистентности данных
Система должна:
- обеспечивать транзакционность критичных операций предметной модели;
- исключать неконтролируемое дублирование сообщений и иных идемпотентных действий;
- иметь предсказуемую модель обработки повторных запросов;
- фиксировать состояние критичных сущностей в основном источнике истины;
- поддерживать восстановление состояния после кратковременного сбоя сервиса.

### 34.9. Требования к локальному кэшу клиента
Клиентский кэш должен:
- ускорять отображение ранее загруженных данных;
- не становиться единственным источником истины по общим сущностям;
- поддерживать инвалидацию и повторную синхронизацию;
- хранить минимально необходимый объём чувствительных данных;
- иметь предсказуемую стратегию очистки и обновления.

### 34.10. Требования к загрузке и хранению файлов
Подсистема вложений должна:
- обрабатывать крупные файлы без помещения бинарного содержимого в основную БД;
- поддерживать асинхронную постобработку;
- обеспечивать проверку размера и типа вложения;
- поддерживать ограничение допустимых форматов и размеров через конфигурацию;
- обеспечивать контроль статуса загрузки и обработки.

Точные лимиты по размеру файлов должны быть утверждены отдельно и зависеть от deployment-конфигурации.

### 34.11. Требования к безопасности
Система должна:
- использовать защищённую передачу данных;
- хранить пароли только в виде стойких hash-значений;
- иметь управляемую модель сессий и отзыв токенов;
- обеспечивать серверную проверку прав доступа;
- ограничивать brute-force и иные типовые злоупотребления;
- защищать чувствительные секреты и ключи от хранения в исходном коде;
- поддерживать аудит критичных действий.

### 34.12. Требования к приватности
Система должна:
- не раскрывать пользователю пространства, каналы и ресурсы, к которым у него нет доступа;
- ограничивать выдачу метаданных о закрытых объектах;
- исключать несанкционированное перечисление закрытых пространств и приглашений;
- обеспечивать управление видимостью профиля и участия пользователя в пределах политики системы.

### 34.13. Требования к наблюдаемости
Система должна:
- формировать структурированные логи;
- поддерживать централизованный сбор логов;
- собирать метрики по API, realtime, звонкам, файловым операциям и безопасности;
- обеспечивать техническую трассировку запросов и межсервисных операций;
- предоставлять health и readiness checks.

### 34.14. Требования к журналированию
Журналирование должно обеспечивать:
- фиксацию ошибок приложений и зависимостей;
- фиксацию событий безопасности;
- фиксацию административных и модераторских действий;
- возможность корреляции событий по request id, session id, user id, workspace id и call session id.

Журналирование не должно приводить к утечке чувствительных секретов, содержимого токенов, необработанных паролей и иных критичных данных.

### 34.15. Требования к резервному копированию и восстановлению
Система должна предусматривать:
- резервное копирование основной БД;
- резервное копирование конфигурации и критичных секретов по отдельной безопасной процедуре;
- резервное копирование или репликацию медиаобъектов в соответствии с политикой deployment-а;
- проверяемую процедуру восстановления;
- документированную политику хранения резервных копий.

### 34.16. Требования к обновлениям и миграциям
Система должна:
- поддерживать миграции схемы БД;
- иметь управляемый порядок обновления модулей;
- не допускать скрытого разрушения данных при обновлении;
- предусматривать совместимость клиентских и серверных версий в пределах допустимого окна обновления.

### 34.17. Требования к конфигурации
Конфигурация системы должна:
- быть внешней по отношению к исполняемому коду;
- поддерживать раздельные профили для локальной, тестовой и серверной среды;
- поддерживать конфигурирование адресов сервисов, лимитов, доменов, сертификатов и политик доступа;
- поддерживать безопасную работу с секретами.

### 34.18. Требования к тестопригодности
Система должна быть спроектирована так, чтобы обеспечивать:
- модульное тестирование доменной логики;
- интеграционное тестирование ключевых межмодульных сценариев;
- проверку корректности миграций;
- тестирование работы прав доступа;
- тестирование reconnect-сценариев;
- тестирование деградации сети и звонков в пределах доступного тестового стенда.

### 34.19. Требования к сопровождаемости
Кодовая база должна:
- быть разделена по понятным модулям и зонам ответственности;
- не допускать неформального дублирования бизнес-логики между клиентом и сервером;
- поддерживать замену инфраструктурных компонентов через контракты и адаптеры;
- сопровождаться технической документацией по ключевым модулям и их взаимодействию.

### 34.20. Требования к эксплуатации первой версии
Первая версия должна ориентироваться на предсказуемую эксплуатацию в условиях малого и среднего числа одновременно активных пользователей без обязательного внедрения сложной распределённой инфраструктуры.

При этом архитектура первой версии не должна закрывать возможность последующего перехода к:
- выделенным media-узлам;
- отдельным узлам realtime-подсистемы;
- вынесенному object storage;
- внешним managed-зависимостям;
- более строгим моделям безопасности и хранения.

## 35. Границы MVP первой версии

### 35.1. Назначение MVP

MVP первой версии должен представлять собой минимально полноценную, архитектурно корректную и эксплуатационно пригодную систему, позволяющую проверить жизнеспособность продукта без внедрения функций, существенно усложняющих разработку, безопасность и сопровождение.

MVP должен подтверждать:
- корректность выбранной клиент-серверной архитектуры;
- работоспособность модели изолированных пространств;
- корректность регистрации, входа и управления сессиями;
- работоспособность обмена сообщениями и вложениями;
- работоспособность звонков и демонстрации экрана;
- применимость ролевой модели и базового разграничения прав;
- переносимость между локальной и серверной средой.

### 35.2. Обязательные функции MVP

В состав MVP первой версии должны входить следующие обязательные функции.

#### 35.2.1. Пользователь и аутентификация
- регистрация пользователя;
- вход пользователя;
- выход из текущей сессии;
- работа access и refresh token механизма;
- базовое управление собственным профилем;
- управление хотя бы одной активной пользовательской сессией.

#### 35.2.2. Пространства и доступ
- создание пространства;
- вступление в пространство по приглашению;
- просмотр доступных пользователю пространств;
- базовое управление участниками пространства;
- назначение базовых системных ролей;
- изоляция пространств друг от друга.

#### 35.2.3. Каналы
- создание текстовых каналов;
- создание голосовых или медиа-каналов;
- просмотр списка доступных каналов;
- базовая настройка видимости канала;
- поддержка приватных каналов в минимально достаточном виде.

#### 35.2.4. Сообщения
- отправка текстовых сообщений;
- получение сообщений в realtime-режиме;
- загрузка истории сообщений;
- редактирование собственных сообщений;
- удаление собственных сообщений;
- удаление чужих сообщений модератором или администратором;
- реакции на сообщения как опционально желательная, но допустимая к упрощению функция.

#### 35.2.5. Вложения
- загрузка файлов;
- прикрепление вложений к сообщениям;
- скачивание и просмотр вложений при наличии доступа;
- базовая асинхронная обработка файлов;
- хранение файлов вне основной реляционной БД.

#### 35.2.6. Realtime и presence
- поддержка постоянного realtime-подключения;
- базовое отображение online/offline статуса;
- доставка новых сообщений и ключевых событий;
- корректное поведение при reconnect.

#### 35.2.7. Звонки
- запуск звонка в допустимом контексте;
- присоединение к звонку;
- выход из звонка;
- использование микрофона;
- использование камеры;
- отображение состояния участников;
- завершение звонка.

#### 35.2.8. Демонстрация экрана
- запуск screen share;
- завершение screen share;
- публикация screen share как отдельного потока;
- отображение активной демонстрации другим участникам;
- передача системного звука при наличии технической поддержки на платформе клиента может входить в MVP только как best-effort функция без требования полной кроссплатформенной унификации.

#### 35.2.9. Безопасность и управление доступом
- server-authoritative проверка прав;
- ролевое разграничение доступа на уровне пространства;
- базовые channel-level ограничения;
- безопасное хранение паролей;
- защищённая передача данных;
- аудит критичных административных действий.

#### 35.2.10. Эксплуатация
- локальный запуск в dev-среде;
- single-node развёртывание;
- конфигурируемость адресов и секретов;
- базовые health-check механизмы;
- базовые структурированные логи.

### 35.3. Что допускается упростить в MVP

Для первой версии допустимы следующие упрощения при условии, что они не ломают архитектурную основу системы.

#### 35.3.1. Пространства и роли
- использовать фиксированный набор системных ролей без полноценного конструктора пользовательских ролей;
- ограничить глубину channel-level permission overrides;
- не реализовывать сложные иерархии категорий каналов сверх минимально необходимого.

#### 35.3.2. Сообщения
- не реализовывать расширенный поиск по сообщениям;
- не реализовывать сложные threaded discussions;
- не реализовывать многоуровневые цитаты, rich formatting и сложные типы системных сообщений сверх необходимого минимума;
- ограничить редактирование и удаление сообщений простой базовой политикой.

#### 35.3.3. Вложения
- ограничить набор поддерживаемых типов файлов;
- ограничить размер вложений разумным конфигурационным лимитом;
- не внедрять сложную серверную медиа-аналитику;
- ограничиться генерацией базовых превью или вовсе отложить часть производной обработки.

#### 35.3.4. Звонки и медиа
- ограничить поддерживаемое число участников звонка эксплуатационным лимитом первой версии;
- не внедрять серверную запись звонков;
- не внедрять MCU/композитинг;
- не внедрять сложные advanced-политики качества сверх базовой адаптации и TURN fallback;
- ограничить client-side media options минимально достаточным набором.

#### 35.3.5. Администрирование
- использовать упрощённую административную панель или технический интерфейс;
- не реализовывать полноценную систему abuse-reporting и appeal workflow;
- ограничить модераторские сценарии базовым набором действий.

### 35.4. Что не входит в MVP

Следующие функции не должны входить в первую рабочую версию.

#### 35.4.1. Федерация и распределённая сеть
- федерация между независимыми deployment-ами;
- автоматическое взаимодействие между разными инсталляциями;
- общая распределённая сеть ресурсов;
- межсерверная репликация пользовательских пространств.

#### 35.4.2. Сложные криптографические модели
- обязательное end-to-end шифрование всех сообщений и вложений;
- кросс-девайсная E2EE синхронизация с управлением пользовательскими ключами;
- сложная модель восстановления ключей и криптографических сессий.

#### 35.4.3. Расширенная коллаборация
- совместное редактирование документов в реальном времени;
- встроенные доски, заметки, задачи и иные подсистемы командной работы за пределами коммуникационного ядра;
- встроенная потоковая трансляция больших мероприятий как отдельный режим.

#### 35.4.4. Расширенная медиа-функциональность
- запись звонков на сервере;
- серверная расшифровка речи;
- автоматические субтитры;
- сложная серверная постобработка медиапотоков;
- виртуальные комнаты со сложной маршрутизацией и медиа-оркестрацией вне базового сценария.

#### 35.4.5. Сложная административная экосистема
- расширенная аналитика поведения пользователей;
- сложные compliance-функции;
- многоуровневая организация tenancy beyond workspace-level;
- межпространственная глобальная директория пользователей и пространств с публичным поиском.

### 35.5. Рекомендуемые эксплуатационные ограничения MVP

Для первой версии должны быть введены явные эксплуатационные ограничения, задаваемые конфигурацией deployment-а.

Следует предусмотреть конфигурируемые лимиты как минимум для:
- максимального размера вложения;
- числа активных приглашений;
- числа участников в пространстве;
- числа каналов в пространстве;
- числа одновременных участников в звонке;
- числа параллельных screen share потоков;
- времени жизни invite-ссылок;
- времени жизни сессий и refresh token политики.

Точные численные значения должны устанавливаться отдельно в эксплуатационной документации и профилях конфигурации.

### 35.6. Критерии архитектурной готовности MVP

MVP считается архитектурно корректным, если:
- система поднимается локально и на удалённом хосте без изменения предметной логики;
- пользователь не видит чужие пространства без доступа;
- сообщения, вложения и звонки работают в пределах заданных ограничений;
- роли и права применяются сервером;
- данные хранятся в предусмотренных источниках истины;
- сбой одного некритичного фонового компонента не разрушает базовые функции обмена сообщениями и аутентификации;
- базовая диагностика позволяет понять причину типовых сбоев.

### 35.7. Критерии, по которым MVP не следует перегружать

MVP не должен расширяться функциями, если их внедрение:
- требует пересмотра базовой модели безопасности;
- требует федерации или межсерверного доверия;
- требует радикального усложнения модели данных;
- требует обязательной сложной криптографической инфраструктуры;
- не увеличивает ценность проверки ядра продукта;
- отвлекает от проверки основных сценариев: доступ, сообщения, вложения, звонки, screen share, роли, переносимость.

### 35.8. Следующий приоритет после фиксации MVP

После фиксации границ MVP следующими приоритетными этапами являются:
- проектирование контрактов API;
- проектирование realtime и signaling событий;
- детализация сценариев жизненного цикла ключевых операций;
- подготовка deployment и runbook документации для локальной и серверной среды.

## 36. Контракты API верхнего уровня

### 36.1. Общие принципы API

Серверный API должен строиться по следующим принципам:
- явное versioning API;
- предсказуемые коды ответа;
- единая модель ошибок;
- идемпотентность там, где клиент может безопасно повторить запрос;
- серверная валидация входных данных;
- пагинация для коллекций;
- фильтрация и сортировка только в явно поддерживаемом объёме;
- отсутствие утечки сведений о недоступных ресурсах.

### 36.2. Общие требования к форматам запросов и ответов

Каждый API-контракт должен предусматривать:
- request id или эквивалентный корреляционный идентификатор;
- серверную временную метку ответа при необходимости;
- формализованный envelope ошибки;
- структуру пагинации для списков;
- структурированные validation errors.

Типовой ответ об ошибке должен включать:
- machine-readable error code;
- человекочитаемое описание;
- контекст ошибки в безопасном объёме;
- correlation identifier.

### 36.3. Группа Auth / Sessions API

#### 36.3.1. Назначение
Подсистема аутентификации должна предоставлять API для:
- регистрации;
- входа;
- обновления access token;
- завершения текущей сессии;
- завершения выбранной пользовательской сессии;
- просмотра активных сессий пользователя.

#### 36.3.2. Базовые операции
Должны быть предусмотрены операции:
- register_user;
- login_user;
- refresh_session;
- logout_current_session;
- logout_selected_session;
- list_user_sessions;
- revoke_other_sessions.

#### 36.3.3. Общие требования
- refresh token не должен передаваться в логах;
- повторный запрос refresh должен иметь контролируемое поведение;
- при отзыве сессии связанные токены должны становиться недействительными;
- ответы не должны раскрывать лишнюю информацию о существовании учётных записей.

### 36.4. Группа Users / Profile API

Подсистема профиля должна предоставлять API для:
- чтения собственного профиля;
- обновления отображаемого имени;
- обновления аватара;
- чтения публично доступных профилей других пользователей в рамках разрешённого контекста;
- просмотра собственных настроек профиля и приватности.

Базовые операции:
- get_my_profile;
- update_my_profile;
- update_my_avatar;
- get_visible_user_profile;
- get_my_profile_settings;
- update_my_profile_settings.

### 36.5. Группа Workspace API

Подсистема пространств должна предоставлять API для:
- создания пространства;
- получения списка доступных пространств;
- чтения пространства по идентификатору;
- изменения базовых настроек пространства;
- получения списка участников;
- изменения членства и ролей при наличии прав.

Базовые операции:
- create_workspace;
- list_my_workspaces;
- get_workspace;
- update_workspace;
- list_workspace_members;
- assign_workspace_role;
- remove_workspace_role;
- remove_workspace_member;
- ban_workspace_member при поддержке санкций в первой версии.

### 36.6. Группа Invite API

Подсистема приглашений должна предоставлять API для:
- создания приглашения;
- получения списка активных приглашений;
- отзыва приглашения;
- валидации приглашения в безопасном объёме;
- вступления по приглашению.

Базовые операции:
- create_workspace_invite;
- list_workspace_invites;
- revoke_workspace_invite;
- validate_invite;
- join_workspace_by_invite.

Требования:
- validate_invite не должен раскрывать лишние данные о пространстве без явной политики;
- join по приглашению должен быть идемпотентным в разумных пределах;
- исчерпанные и отозванные приглашения должны возвращать контролируемые ошибки.

### 36.7. Группа Channel API

Подсистема каналов должна предоставлять API для:
- создания канала;
- чтения списка каналов пространства;
- чтения конкретного канала;
- обновления настроек канала;
- удаления или архивирования канала;
- управления членством приватного канала;
- управления channel-level разрешениями.

Базовые операции:
- create_channel;
- list_workspace_channels;
- get_channel;
- update_channel;
- delete_or_archive_channel;
- add_channel_member;
- remove_channel_member;
- update_channel_permissions.

### 36.8. Группа Message API

Подсистема сообщений должна предоставлять API для:
- отправки сообщения;
- получения истории сообщений;
- редактирования сообщения;
- удаления сообщения;
- добавления и удаления реакции;
- получения указателей прочтения или обновления read marker.

Базовые операции:
- create_message;
- list_messages;
- get_message при необходимости;
- edit_message;
- delete_message;
- add_message_reaction;
- remove_message_reaction;
- update_read_marker.

Требования:
- create_message должен поддерживать client_message_id или иной механизм идемпотентности;
- list_messages должен поддерживать cursor-based пагинацию;
- редактирование и удаление должны проверять права доступа и состояние сообщения;
- история не должна возвращать сообщения из недоступного контекста.

### 36.9. Группа Attachment API

Подсистема вложений должна предоставлять API для:
- инициации upload session;
- завершения upload session;
- привязки объекта к сообщению;
- получения метаданных вложения;
- скачивания или получения временной ссылки к объекту.

Базовые операции:
- create_upload_session;
- complete_upload_session;
- get_media_object;
- get_media_download_reference;
- attach_media_to_message в явном или неявном виде.

### 36.10. Группа Call / Media Session API

Подсистема звонков должна предоставлять API для:
- создания call session;
- получения состояния звонка;
- присоединения к звонку;
- выхода из звонка;
- завершения звонка;
- публикации намерения на screen share;
- получения технических параметров для media-orchestration.

Базовые операции:
- create_call_session;
- get_call_session;
- join_call_session;
- leave_call_session;
- end_call_session;
- start_screen_share_intent;
- stop_screen_share_intent.

Примечание:
- реальный обмен медиапараметрами и сигналингом может происходить через отдельный realtime/signaling канал, а не только через обычный request-response API.

### 36.11. Группа Admin / Audit API

Административная подсистема должна предоставлять API для:
- чтения журналов модерации;
- чтения аудита пространства;
- чтения security events при наличии прав;
- применения ограниченных модераторских действий.

Базовые операции:
- list_audit_events;
- list_moderation_actions;
- list_security_events;
- timeout_member;
- kick_member;
- ban_member;
- unban_member при наличии сценария восстановления.

### 36.12. Требования к ошибкам API

Для всех API должны использоваться стабильные error codes, как минимум для классов ошибок:
- authentication_failed;
- authorization_denied;
- validation_failed;
- resource_not_found_or_not_visible;
- conflict;
- rate_limited;
- invite_invalid;
- invite_expired;
- invite_revoked;
- session_revoked;
- message_already_processed;
- media_upload_invalid;
- call_state_invalid.

## 37. Контракты realtime и signaling

### 37.1. Общие принципы realtime-взаимодействия

Realtime-подсистема должна обеспечивать:
- постоянное клиентское соединение;
- подписку на события в рамках доступных пользователю контекстов;
- доставку событий с контролируемой моделью подтверждения при необходимости;
- повторную синхронизацию состояния после reconnect;
- разделение бизнес-событий, presence-событий и signaling-событий.

### 37.2. Категории realtime-событий

События должны быть разделены как минимум на следующие категории:
- connection events;
- presence events;
- workspace and channel events;
- message events;
- invite and membership events;
- call and media session events;
- signaling events;
- moderation and system events.

### 37.3. Connection events

Realtime-канал должен поддерживать события:
- connected;
- connection_ready;
- reconnect_required;
- resync_required;
- server_shutdown_notice при необходимости;
- heartbeat или equivalent keepalive semantics.

### 37.4. Presence events

Должны поддерживаться события:
- presence_updated;
- user_online;
- user_offline;
- typing_started;
- typing_stopped.

Примечание:
- presence-события являются краткоживущими и не требуют такой же модели надёжности, как события сообщений.

### 37.5. Workspace and membership events

Должны поддерживаться события:
- workspace_created;
- workspace_updated;
- workspace_membership_changed;
- role_assignment_changed;
- invite_created при необходимости в админском контексте;
- invite_revoked при необходимости;
- channel_created;
- channel_updated;
- channel_deleted_or_archived;
- channel_visibility_changed.

### 37.6. Message events

Должны поддерживаться события:
- message_created;
- message_updated;
- message_deleted;
- message_reaction_added;
- message_reaction_removed;
- read_marker_updated.

Требования:
- message_created должен содержать server-generated идентификатор, контекст и метаданные источника;
- клиент должен иметь возможность сопоставить message_created с ранее отправленным client_message_id;
- события сообщений должны быть пригодны для resync после временного разрыва соединения.

### 37.7. Call and media events

Должны поддерживаться события:
- call_created;
- call_state_changed;
- call_participant_joined;
- call_participant_left;
- participant_media_state_changed;
- screen_share_started;
- screen_share_stopped;
- call_ended.

### 37.8. Signaling events

Сигналинговый контур должен поддерживать как минимум:
- call_invitation;
- call_acceptance или equivalent participant readiness;
- session_description_offer;
- session_description_answer;
- ice_candidate_published;
- media_negotiation_required;
- signaling_error;
- call_join_denied;
- call_context_expired.

Требования:
- signaling events должны быть строго привязаны к call session и участнику;
- клиент не должен иметь возможность публиковать signaling в чужую call session;
- signaling payloads должны валидироваться сервером в безопасном объёме.

### 37.9. Ack и resync модель

Realtime-подсистема первой версии должна предусматривать:
- минимальную модель подтверждения клиентских действий там, где необходима корреляция;
- серверные события о результате команд;
- возможность полной или частичной resync после reconnect;
- использование cursor, revision или event offset модели для восстановления последовательности.

### 37.10. Требования к изоляции событий

Пользователь через realtime-канал не должен получать:
- события чужих пространств;
- события закрытых каналов без доступа;
- signaling-события чужих звонков;
- административные и модераторские события без соответствующих прав.

## 38. Сценарии жизненного цикла ключевых операций

### 38.1. Регистрация пользователя

Жизненный цикл регистрации должен включать:
- отправку данных регистрации клиентом;
- серверную валидацию;
- создание учётной записи;
- создание базового профиля;
- создание первой сессии или выдачу возможности входа в отдельном шаге;
- аудит события регистрации.

### 38.2. Вход пользователя

Жизненный цикл входа должен включать:
- передачу учётных данных;
- проверку credentials;
- создание или обновление device session;
- выдачу access и refresh token;
- аудит события входа;
- установление realtime-подключения после успешной аутентификации.

### 38.3. Создание пространства

Жизненный цикл должен включать:
- запрос на создание пространства;
- создание записи workspace;
- назначение создателю роли owner;
- создание базовых системных ролей;
- создание стартового набора каналов при наличии политики bootstrap;
- публикацию событий о создании пространства в рамках доступного контекста.

### 38.4. Вступление по приглашению

Жизненный цикл должен включать:
- ввод или активацию invite;
- валидацию invite;
- проверку лимита, срока действия и статуса приглашения;
- создание membership;
- назначение стартовой роли;
- публикацию membership event;
- обновление клиентского списка доступных пространств.

### 38.5. Отправка сообщения

Жизненный цикл должен включать:
- формирование клиентом сообщения с client_message_id;
- серверную проверку права на отправку;
- запись сообщения в основной источник истины;
- привязку вложений при наличии;
- публикацию message_created;
- подтверждение клиенту;
- корректную обработку повторной отправки при сетевом сбое.

### 38.6. Редактирование и удаление сообщения

Жизненный цикл должен включать:
- проверку права на изменение;
- изменение состояния сообщения или создание revision;
- публикацию message_updated или message_deleted;
- обновление клиентского представления.

### 38.7. Загрузка вложения

Жизненный цикл должен включать:
- инициацию upload session;
- валидацию размера и типа;
- передачу бинарного объекта в object storage;
- подтверждение завершения загрузки;
- создание media_object metadata;
- постановку задач постобработки при необходимости;
- связывание вложения с сообщением.

### 38.8. Подключение realtime-клиента

Жизненный цикл должен включать:
- аутентификацию realtime-соединения;
- определение доступных пользователю контекстов;
- выдачу начального состояния или точки синхронизации;
- подписку на разрешённые категории событий;
- heartbeat/keepalive;
- переход в reconnect flow при обрыве.

### 38.9. Reconnect и resync

Жизненный цикл reconnect должен включать:
- повторную аутентификацию или проверку действительности сессии;
- восстановление realtime-соединения;
- определение пропущенного диапазона событий;
- resync списка пространств, каналов, сообщений и call state в допустимом объёме;
- восстановление локального клиентского состояния.

### 38.10. Создание и вход в звонок

Жизненный цикл звонка должен включать:
- создание call session в допустимом контексте;
- публикацию события о звонке;
- присоединение участников;
- серверную валидацию членства и прав;
- получение клиентом сигналингового контекста;
- начало media negotiation;
- фиксацию participant state.

### 38.11. Демонстрация экрана

Жизненный цикл screen share должен включать:
- проверку права на screen share;
- получение клиентом разрешения ОС на захват;
- уведомление сервера о старте screen share;
- публикацию screen_share_started;
- публикацию отдельного media track;
- обновление состояния участников;
- корректное завершение при явной остановке или потере источника.

### 38.12. Исключение, ограничение и блокировка участника

Жизненный цикл модераторского действия должен включать:
- серверную проверку полномочий инициатора;
- применение санкции;
- изменение membership state при необходимости;
- публикацию событий об изменении доступа;
- запись в audit log и moderation log;
- немедленное прекращение доступа нарушителя к недоступным ресурсам.

## 39. Threat model и требования безопасности низкого уровня

### 39.1. Назначение threat model

Threat model должна использоваться для фиксации реальных угроз первой версии и выбора достаточных мер защиты без избыточного усложнения архитектуры.

### 39.2. Основные классы угроз

Для первой версии должны учитываться как минимум следующие классы угроз:
- компрометация учётной записи пользователя;
- подбор паролей и brute-force;
- кража или повторное использование токенов;
- несанкционированный доступ к закрытым пространствам;
- обход проверки прав через API или realtime;
- enumeration invite-кодов, пространств или ресурсов;
- злоупотребление загрузкой файлов;
- утечка содержимого через логи, дампы, резервные копии или object storage;
- компрометация сессий при reconnect и многосессионной работе;
- злоупотребление signaling и звонками;
- DoS или частичный DoS на уровне API, realtime, TURN и загрузки файлов;
- компрометация административных интерфейсов.

### 39.3. Требования к защите аутентификации

Система должна предусматривать:
- стойкое хэширование паролей;
- rate limiting на операции входа и регистрации;
- аудит неуспешных попыток входа;
- ограничение информативности ошибок логина;
- отзыв сессий;
- привязку сессий к контексту устройства в разумном объёме;
- безопасную ротацию refresh token при выбранной модели.

### 39.4. Требования к защите авторизации

Система должна предусматривать:
- серверную проверку прав для каждого критичного действия;
- запрет доступа к объектам за пределами membership;
- безопасную обработку прямого обращения по идентификаторам;
- единый permission evaluation layer;
- отсутствие доверия клиентским флагам и ролям без проверки на сервере.

### 39.5. Требования к защите invites

Система должна предусматривать:
- достаточную энтропию invite-кодов;
- срок жизни invite;
- отзыв invite;
- лимит использования;
- rate limiting на проверку invites;
- защиту от массового enumeration invite-параметров.

### 39.6. Требования к защите сообщений и вложений

Система должна предусматривать:
- проверку доступа к сообщению и вложению перед выдачей;
- ограничение допустимых размеров файлов;
- проверку MIME/type и расширения в допустимом объёме;
- безопасную работу с именами файлов и метаданными;
- исключение прямой публичной выдачи приватных объектов без проверки полномочий или без контролируемых временных ссылок;
- политику безопасной постобработки медиафайлов.

### 39.7. Требования к защите realtime и signaling

Система должна предусматривать:
- аутентификацию realtime-соединения;
- привязку signaling к конкретной call session и участнику;
- валидацию signaling payloads;
- ограничения частоты signaling-команд;
- запрет публикации signaling в чужой контекст;
- прекращение доступа к событиям после потери прав или завершения сессии.

### 39.8. Требования к защите медиа и звонков

Система должна предусматривать:
- валидацию права на join_call;
- валидацию права на start_screen_share;
- защиту TURN и media endpoints от несанкционированного использования;
- ограничение ресурсоёмких сценариев конфигурационными лимитами;
- журналирование ключевых событий звонков.

### 39.9. Требования к защите секретов

Система должна предусматривать:
- хранение секретов вне исходного кода;
- разделение секретов по средам;
- безопасную ротацию секретов в допустимом объёме;
- защиту приватных ключей, токенов доступа к storage и параметров интеграций.

### 39.10. Требования к логам и резервным копиям

Система должна предусматривать:
- исключение чувствительных значений из логов;
- контролируемый доступ к логам;
- шифрование и защиту резервных копий в соответствии с deployment-политикой;
- проверяемую процедуру восстановления без утраты контроля доступа.

### 39.11. Требования к административным интерфейсам

Система должна предусматривать:
- отдельный контроль доступа к административным и модераторским функциям;
- аудит административных действий;
- ограничение перечня пользователей, имеющих доступ к служебным данным;
- минимизацию экспозиции внутренних диагностических интерфейсов.

### 39.12. Ограничения security scope первой версии

Первая версия не обязана включать:
- полноценный zero-trust межузловой security framework;
- сложную HSM/KMS-интеграцию как обязательный элемент;
- обязательную E2EE-модель;
- расширенные compliance-функции корпоративного уровня.

Однако архитектура не должна блокировать их добавление в будущем.

## 40. Требования к развёртыванию и runbook-документации

### 40.1. Общие положения

Для системы должна быть подготовлена эксплуатационная документация, обеспечивающая повторяемое развёртывание и сопровождение в следующих режимах:
- локальная среда разработки;
- single-node серверный режим;
- internet-facing deployment с публичным доступом.

### 40.2. Состав эксплуатационной документации

Эксплуатационная документация должна включать:
- описание состава модулей;
- перечень обязательных зависимостей;
- описание конфигурационных параметров;
- описание переменных окружения и секретов;
- порядок первого запуска;
- порядок миграций БД;
- порядок запуска фоновых workers;
- порядок подключения object storage;
- порядок подключения Redis и брокера;
- порядок подключения STUN/TURN;
- порядок обновления системы;
- порядок резервного копирования и восстановления;
- порядок базовой диагностики типовых сбоев.

### 40.3. Требования к локальному запуску

Локальный режим должен документировать:
- минимальный набор сервисов для разработки;
- способ инициализации БД;
- создание тестового администратора или начальной учётной записи;
- запуск клиента и backend-компонентов;
- настройку локального object storage backend или его упрощённого аналога;
- упрощённый режим конфигурации STUN/TURN для локального тестирования при необходимости.

### 40.4. Требования к single-node развёртыванию

Single-node runbook должен документировать:
- состав процессов или контейнеров;
- порядок запуска и рестарта;
- размещение логов;
- подключение домена или внутреннего DNS;
- подключение TLS;
- параметры хранилищ и резервного копирования;
- базовые лимиты для production-like среды малого масштаба.

### 40.5. Требования к internet-facing deployment

Runbook для публичного развёртывания должен документировать:
- требования к доменному имени;
- порядок получения и продления TLS-сертификатов;
- правила публикации API и realtime endpoints;
- правила публикации signaling и TURN-инфраструктуры;
- сетевые требования и открываемые порты;
- базовые требования к firewall и reverse proxy;
- рекомендации по защите публичных endpoint-ов.

### 40.6. Требования к конфигурации среды

Runbook должен содержать перечень конфигурационных параметров как минимум для:
- базы данных;
- Redis;
- брокера сообщений;
- object storage;
- auth secrets;
- session policy;
- invite policy;
- media limits;
- upload limits;
- domain and TLS settings;
- STUN/TURN configuration.

### 40.7. Требования к процедурам обновления

Runbook должен описывать:
- порядок применения миграций;
- совместимость клиентской и серверной версии;
- порядок обновления без потери данных;
- rollback strategy в допустимом объёме;
- порядок проверки после обновления.

### 40.8. Требования к резервному копированию и восстановлению

Runbook должен описывать:
- что резервируется;
- как часто резервируется;
- где хранится резервная копия;
- как проверяется корректность резервной копии;
- как выполняется восстановление БД, конфигурации и медиаобъектов;
- какие данные могут быть потеряны при выбранной политике бэкапов.

### 40.9. Требования к диагностике типовых сбоев

Runbook должен содержать базовые инструкции по диагностике сценариев:
- пользователь не может войти;
- invite не работает;
- сообщения не доставляются;
- realtime-соединение не устанавливается;
- звонок создаётся, но медиапотоки не устанавливаются;
- screen share не запускается;
- upload завершается ошибкой;
- Redis, БД или broker недоступны;
- TURN не обеспечивает relay в проблемной сети.

### 40.10. Требования к минимуму артефактов развёртывания

Для первой версии должны существовать как минимум:
- пример конфигурации окружения;
- инструкция локального запуска;
- инструкция single-node запуска;
- инструкция internet-facing развёртывания;
- инструкция резервного копирования;
- инструкция базовой диагностики.

После завершения настоящего документа система должна считаться описанной на уровне, достаточном для перехода к:

Более низкоуровневые спецификации, включая точные форматы полей, схемы событий, таблицы DTO, схемы БД и конкретные стековые решения, должны разрабатываться как уточняющие документы без разрушения зафиксированных здесь принципов.
